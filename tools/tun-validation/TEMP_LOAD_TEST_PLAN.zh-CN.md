# QDC507 tun.ko 受控临时加载测试方案

2026-11-13。**本次交付只准备方案，没有连接模块、上传文件、加载驱动、创建接口或执行恢复。** 后续测试分为“加载、打开、创建、收发、卸载”五项验收，每项单独记录结果，失败即停止向后推进。静态核验见 [关键 ABI 报告](TUN_ABI_AUDIT.zh-CN.md)。

本方案的显式设备操作限定在已有 RAM 文件系统、内核临时状态和测试进程自己的网络命名空间内。模块加载是全局内核操作，网络命名空间不能隔离内核 ABI 错误或阻止整机崩溃。临时文件不写入闪存，也不等于整个运行系统绝不会由既有日志/设备管理服务产生持久记录。

## 二、实施前必须满足的条件

### 电脑上先准备，不碰设备

1. 重新核对以上驱动摘要，保存产物、ABI 报告和本方案的 Git 提交号。
2. 准备一个**收到 ADB WRTE 数据即向电脑文件输出**的执行通道，使用同一个 USB 所有者，禁用自动重启、自动 USB reset、自动重连后重放命令及 AT 初始化。用模拟传输验证收到部分输出后超时、断线时，已有日志仍在电脑上，非零退出状态和缺失结束标记均能被识别。
3. 准备有界的内核日志读取器和 TUN 测试器。测试器需使用目标兼容的 ARM 用户态 ABI；在电脑上核对 ELF、依赖、资源上限和下面的接口调用顺序。**本轮未编写或验证这些执行工具，不能把方案中的测试器描述当作已经存在的可执行程序。**

本机 CellBridge 项目中对应 `/tmp/dji-iphone-tools/qdc507-adb` 的 CLI 源码只适合参考；实际执行工具的版本和行为仍需验收：

- `Client.Shell` 使用 `strings.Builder` 累积输出，返回后 CLI 才打印；`tee`、`stdbuf` 不能把它变成实时日志通道。
- 同一客户端的 Shell 用互斥锁串行执行，USB 也只能有一个独立进程占用。不能另外开一个 `dmesg -w` 进程抢占 USB。
- 老版 `shell:` 协议没有远端退出码，必须由远端打印结束标记和实际状态，不能只看主机进程退出码。
- `recover` 可能请求 `reboot:`，随后重新枚举 USB 并初始化 AT 设置；`start/stop/script run` 面向语音业务。**这些命令都不作为本测试的默认诊断或自动恢复入口。**

### 设备侧先做只读检查，再决定是否进入测试

以下状态必须在实际测试当天重新采集；旧记录不代表当前状态：

| 条件 | 核验方式和不满足时的处理 |
| --- | --- |
| 目标身份和内核未变 | USB 身份、`uname -a`、`/proc/version`、`/proc/config.gz` 摘要；不符则停止，重新评估产物 |
| 有权限且允许模块操作 | `id`、进程 status 的 CapEff/CapBnd、`/proc/sys/kernel/modules_disabled`；root 身份不能代替 CAP_SYS_MODULE、建网络命名空间及管理网络所需权限。权限不足或开关为 1 时停止，不修改该开关 |
| 没有已有 TUN 使用者 | 保存 `/proc/modules`、`/proc/misc` 和当前网络设备；若 tun 已存在、次设备号 200 被占用或现有 TUN 无法归属，则不加载、不卸载已有对象 |
| 暂存确实位于 RAM | 解析 `/proc/mounts` 或 mountinfo，解析目录真实路径，核对最近挂载点、tmpfs 类型及剩余空间；不能假定 `/tmp` 在内存中 |
| 测试节点和程序可用 | 节点所在 RAM 挂载不能有 nodev，程序所在 RAM 挂载不能有 noexec。没有合适路径则停止，不重挂载系统分区或绕到闪存暂存 |
| 内存有余量 | 取 3 份、间隔 5 秒的 meminfo。建议准入值为每次 `MemAvailable >= 10 MiB`，测试暂存和新增用户进程预算合计不超过 2 MiB；这是本方案的保守控制值，不是驱动内存实测 |
| 内核日志可读且可及时传出 | 原厂配置日志缓冲约 8 KiB，`CONFIG_PSTORE=n`。验证日志读取、主机落盘和序号/截断识别；缺失则不加载 |
| 恢复手段在现场 | 明确供电方式，确认有人能中断模块的全部实际供电；拔 USB 不一定等于断电。UART/独立控制台当前未验证，不把它写成已有能力 |
| 业务和 USB 所有者明确 | 无正在进行的通话或关键业务；确认已有网关/管理程序及自动重连行为。需要暂停主机网关时先确定影响和恢复命令，不抢占、不盲停、不自动启用原本没运行的服务 |

同时只读检查既有 hotplug/mdev/udev 和网络管理规则是否会对新 misc/TUN 设备执行自动配置。不能以测试隔离为由修改它们；存在会修改主网络或持久配置的未隔离规则时，先停在准备阶段。

采集配置为 `CONFIG_NET_NS=y`、`CONFIG_MODULE_UNLOAD=y`、`CONFIG_MODULE_FORCE_UNLOAD=y`、`CONFIG_MODULE_SIG=n`、`CONFIG_WATCHDOG=n`、`CONFIG_MAGIC_SYSRQ=n`、`CONFIG_PSTORE=n`。实际启动状态、节点和用户态命令是否可用仍须现场检查。强制卸载虽被编译支持，本方案禁止使用。

## 三、日志如何采集和保存

### 主机目录及内容

每轮在电脑的 `tun-validation-local/runtime-logs/<RUN_ID>/` 新建独立目录，例如 `20261113-01`；`RUN_ID` 必须唯一，不覆盖既有结果。设备日志只保存在这里，不写入模块数据分区，不提交到 Git。

```text
manifest.json                驱动/配置摘要、方案提交号、主机时间和目标身份
preflight/                   完整只读基线、USB 所有者、挂载和业务状态
events.jsonl                 阶段开始/结束、远端状态、主机状态、超时和断线事件
kernel.raw.log               连续内核日志原文，不先 grep，不覆盖、不清空
transport.raw.log            USB/ADB 原始输出与错误，保留断线前的部分数据
samples.jsonl                uptime、内存、模块占用、测试进程资源和阶段标签
stages/                      每个阶段的 stdout/合并输出、状态及前后快照
cleanup/                     接口、FD、模块引用、节点、文件和主网络回读
recovery/                    仅异常时生成：最后响应、USB 变化、恢复动作及新启动信息
result.md                    分项结果、缺失证据、剩余状态和是否需要恢复
```

`events.jsonl` 的每个事件保存主机 Asia/Shanghai 时间、可用时的设备 uptime、boot_id、阶段名和状态；不为对时而改设备时钟。每次危险步骤前先把基线和阶段 BEGIN 事件刷到电脑文件；收到阶段结束数据后也及时刷盘。原文保留，便于判断错误来自加载器、测试器还是控制通道。

### 采集项目

- **加载前、每阶段后、清理后**：`uname`、boot_id/uptime、`/proc/modules`、`/proc/misc`、`/proc/sys/kernel/tainted`、`/proc/meminfo`、`/proc/vmstat` 的 OOM/分配失败相关项（存在时）、测试 PID 的 status/stat、`/sys/module/tun` 的 refcnt/holders（存在时）。
- **主网络基线及清理对照**：网络设备名/ifindex/MTU/地址、全部已存在路由表及规则、IPv6 路由、DNS 配置摘要和防火墙规则快照；只用已核实可用的只读查询方式，不因缺少命令而安装软件或加载额外模块。业务只读记录服务健康和队列计数，不产生对外短信/呼叫。
- **内核原文**：优先只读打开 `/dev/kmsg`，保留其序号和单调时间；每轮记录起止序号、EPIPE、序号缺口和传输截断。读取器与阶段动作共用一个控制通道，在远端作为有界子进程运行并用精确 PID 清理；不另开 USB 客户端。
- 不读会竞争消耗全局日志的 `/proc/kmsg`，不执行 `dmesg -c`、清日志、写 `/dev/kmsg`、修改 printk 等 sysctl。若现场只有普通 dmesg，只能得到非清空快照；证据能力降低，须先解决实时日志前置条件，不能把快照说成连续崩溃日志。
- 主机传输层必须保留超时前已收到的数据。远端每项动作打印带唯一 RUN_ID 的 BEGIN、END、`RC=<实际状态>`；缺失 END、远端非零、USB 错误或主机超时都记为失败/状态未知，不以输出里出现“成功”字样替代验收。

8 KiB 环形缓冲可能覆盖，崩溃时尚未传出的最后记录也可能丢失。此方案不能保证拿到完整 panic 栈；若要求完整硬故障记录，须在执行前另行准备并验证独立串口/控制台，不能靠事后重启补回。

## 四、分阶段测试和通过标准

每一阶段结束后先审核日志和现场状态，再人工决定是否继续；不把下面所有步骤串成自动执行脚本。**此处的设备动作均为未来授权后的计划，本轮未执行。**

### S0 基线、暂存和日志就绪

先完成第二、三节的只读检查。在已经确认的 tmpfs 上，以 umask 077 创建权限 0700 的独立测试目录，仅暂存核对过摘要的驱动及必要测试工具；逐个记录创建路径和 PID。完整接收文件后先在设备核对长度和 SHA-256，再与电脑值比较，不能边接收边加载。若设备没有摘要命令，可将文件完整读回电脑核验；不能跳过校验。

日志读取器先发 READY，电脑验证数据已落盘后才允许后续加载。不要为了诊断触碰 TUN 字符设备：**打开设备本身就会进入驱动代码，还可能触发自动加载**。此阶段不调用 `modprobe`，不更新模块索引。

通过标准：身份、产物、RAM 路径、资源、日志、控制所有权和现场恢复条件均满足，原业务基线已保存。

### S1 仅加载模块，观察 30 秒

使用正常 `insmod` 和已核对的 RAM 绝对路径，只执行一次；不带 force，不跳过 vermagic，不自动重试。示意命令为 `insmod "$RAM_MODULE"`，其中变量仅在 S0 完成并记录后设置。主机对加载返回最多等待 10 秒；返回成功后另观察 30 秒。超时不表示内核已经取消加载，按状态未知处理。

通过必须同时满足：远端退出状态为 0；`/proc/modules` 出现 tun 且完成初始化；`/proc/misc` 出现 `200 tun`；sysfs 可用时对应 misc 设备号为 `10:200`；没有新 TUN 网络接口、内核异常或业务退化。记录模块实际大小和引用计数。

`insmod` 返回 0 只证明这一项加载验收通过，不代表字符设备打开、TUN 创建或收发可用。未进入后续测试时不主动打开节点。

### S2 仅打开/查询/关闭，最长 10 秒

优先使用测试专属字符节点，路径位于预先确认允许设备节点的 RAM 挂载内：`mknod "$TEST_TUN_NODE" c 10 200`，权限 0600。不覆盖、改权限或替换已有 `/dev/net/tun`。如果由现有设备管理器自动生成标准节点，记录其变化；私有别名不能阻止其他进程打开同一驱动，仍须检查引用和所有者。

测试器以 `O_RDWR|O_NONBLOCK|O_CLOEXEC` 打开，调用 `TUNGETFEATURES`、记录结果，然后关闭；此阶段不调用 `TUNSETIFF`。不继承 FD 给后台进程。

通过标准：打开、查询和关闭均成功；不出现测试网络接口；引用计数在关闭后回落；内核日志正常。节点创建成功本身不证明驱动可用。

### S3 创建一个非持久 TUN，关闭验证删除，最长 30 秒

测试器先 `unshare(CLONE_NEWNET)`，验证自己与父控制进程的网络命名空间不同，再打开 TUN。创建失败时不得退回主网络命名空间继续。

调用 `TUNSETIFF`，指定 `IFF_TUN|IFF_NO_PI|IFF_TUN_EXCL`，使用固定测试名 `qdcvt0`，只建一条队列。若同名已存在则报错，不附着。不开 TAP、多队列、vnet header，不调用 `TUNSETPERSIST`，也不用会建立持久 TUN 的 `ip tuntap add`。

暂不配置地址。记录本命名空间内的接口类型和 MTU，保持最多 10 秒，然后显式关闭 FD。测试进程在退出命名空间前，用 ioctl/RTNETLINK 核对接口已不存在，再退出。**不使用未重新挂载的 `/sys/class/net` 视图证明私有命名空间状态**；采用本进程的 `/proc/self/net/*` 或网络 ioctl/RTNETLINK，避免读到主命名空间的 sysfs 视图。

通过标准：新接口只在私有命名空间可见；关闭最后一个非持久 FD 后接口确实消失；进程退出后没有遗留命名空间引用。不能仅靠“进程退出了”推定清理成功。

### S4 私有命名空间内双向收发，最长 30 秒

前一阶段成功且内存仍满足条件时，用新的测试进程/私有网络命名空间重复创建非持久单队列 TUN。只在该命名空间内设置：本地 `192.0.2.1`、对端 `192.0.2.2`、掩码 `/30`、测试 MTU 1500、接口 UP；无默认路由、无物理设备、无跨命名空间 veth，不改主网络配置。调用 `TUNSETOFFLOAD=0`，不使用 GSO 或校验和卸载。

1. UDP socket 绑定本地测试地址和端口，向对端测试地址发一个带 RUN_ID、方向、序号和固定内容的短 UDP 数据报。
2. 从 TUN FD 读到 IPv4 包，核对协议、地址、端口、长度、序号和负载；这是 **内核 → TUN FD** 的证据。
3. 测试器构造反向 IPv4/UDP 包，正确计算 IP 与 UDP 校验和，从 TUN FD 写入，再由本地 UDP socket 收到对应负载；这是 **TUN FD → 内核协议栈/UDP** 的证据。
4. 共做 10 组，不超过每秒 10 组，UDP 负载不超过 256 字节；每次 poll/收包等待最多 2 秒。读取缓冲上限 2048 字节，不缓存无限队列。发现无关包时有界记录，累计超过 32 包或总观察数据超过 64 KiB 则停止，不用忙循环清队列。
5. 保存双向序号/负载核对结果与测试接口收发计数；计数只能作旁证，不能替代实际收到正确包。随后关闭 UDP、TUN、控制 socket，再验证接口消失并退出命名空间。

通过标准：10 组双向内容逐一匹配，无超时、异常丢包、OOM、内核警告或主业务变化；关闭后接口、FD 和测试进程均消失。此结果只证明最小 IPv4 单队列通路，不证明 IKEv2/IPsec、IPv6、多队列或长期稳定性。

### S5 正常卸载、清理和 30 秒回读

按第五节顺序清理。本轮首次实测最多一个完整加载/卸载周期，S3 与 S4 各做一次生命周期；不做自动反复重载、压力测试或故障注入。

## 五、正常清理顺序

仅在内核和控制通道保持健康时执行：

1. 停止测试发包，等待测试器主动关闭所有 FD；若超时，仅对清单中的确切 PID 发 TERM。发信号前核对 PID 的 starttime、exe 和父子关系，不用 `pkill -f` 或按“tun”模糊匹配。必要的 KILL 只针对已核实的本轮用户进程；D 状态或关闭路径卡住时转异常恢复，不强行推进。
2. 测试器在自己的命名空间内证明 `qdcvt0` 已删除；核对 PID 退出且没有其他进程、FD、bind mount 或命名空间句柄保留该命名空间。本方案不使用 `ip netns add` 或 `/var/run/netns` 持久绑定。
3. 检查 `/proc/modules` 的 tun 引用、sysfs refcnt/holders 及本轮 FD 所有者；短暂 RCU 清理可等待数秒再检查。仍被占用时先定位归属，不停无关业务，不循环尝试卸载。
4. 确认无引用后只做一次普通 `rmmod tun`，记录远端状态和内核日志，主机最多等待返回 10 秒。**禁止 `rmmod -f`、忽略 vermagic、修改 modules_disabled 或清除 taint。**
5. 回读 `/proc/modules`、`/proc/misc` 和 sysfs，确认 tun、`200 tun` 及模块/设备注册项均已消失。若卸载返回错误、卡住或对象仍在，不能宣称已卸载。
6. 仅删除创建清单中的私有节点、暂存驱动及测试工具文件，再用 `rmdir` 删除已空的私有目录。不使用对任意变量目录的递归删除。已有共享节点保留原状；设备管理器生成的标准节点由其正常清理，残留时记录并复核，不盲删共享路径。
7. 采集清理后日志和状态，比较主网络地址、路由、规则、DNS、防火墙和原业务健康。配置项应与基线一致；设备计数器、uptime、日志、随机地址和进程 PID 等动态值单独解释，不要求原始文件逐字相同。
8. 停止并回收本轮日志子进程；如曾暂停主机服务，仅恢复测试前确实运行的服务，核对原业务路径。停止日志进程前先将最后快照落到电脑。
9. 再观察 30 秒内存和内核日志，给出“加载、打开、创建、双向收发、卸载、清理、业务恢复”七项独立结果。没有泄漏趋势证据时也只记短时观察，不宣称长期稳定。

删除 RAM 中的 `.ko` 文件不等于卸载模块；关闭主机 USB 会话不等于关闭远端所有 FD；设备重启后的新内核不能用来证明旧内核曾成功卸载。

内核 taint 即使在卸载后也可能保留到重启，不能通过清理文件复原。当前产物为 GPL、`intree=Y` 且采集配置禁用 MODULE_SIG，不预设“增加 taint 是正常的”；任何新增 bit 都须按含义判断，新 Oops/WARN/强制加载/强制卸载标记按失败处理。

## 六、停止条件与恢复阶梯

### 任一条件出现，停止下一阶段

- 新出现 Oops、BUG、WARNING、NULL pointer、页错误、slab/链表破坏、锁死、RCU stall、OOM 或分配失败。
- ELF/vermagic/符号错误、接口或节点归属异常、远端非零、缺少结束标记、USB 断开、设备 uptime/boot_id 意外变化。
- 日志序号缺口、日志通道失效、主机文件写入失败或磁盘预算不足；主机日志预算先预留至少 10 MiB，不以静默截断维持测试。
- `MemAvailable < 6 MiB`，或相对同等阶段基线持续下降超过 4 MiB，或新增用户进程/暂存超出 2 MiB 预算。阈值是停止策略；本方案不通过 drop_caches、kill 系统服务、加 swap 或修改 OOM 设置腾内存。
- 主业务掉线、主网络配置变化、非测试接口受到影响或有人开始通话等不适合继续的现场事件。

**超时只表示主机停止等待，不能撤销已经进入内核的 insmod、ioctl、close 或 rmmod。** 不自动重发这些命令。

### 按现场状态处理

| 现场状态 | 处理和恢复 |
| --- | --- |
| 普通加载失败，内核和 shell 正常 | 保存错误及完整内核日志，核对模块/设备是否残留；按实际状态正常清理 RAM 文件，不 force、不换参数重试 |
| 用户态测试失败，内核健康 | 停发包、按精确 PID/FD 正常关闭，再执行第五节清理；保留失败包和状态，不继续后续功能测试 |
| 普通卸载忙或引用不明 | 记录 refcnt、holders、FD 和进程状态；只处理本轮归属。无法释放则记“卸载未完成”，保留现场，进入已获准的恢复分支，不使用强制卸载 |
| 出现 Oops/内核破坏但仍有响应 | 及时保存已收到日志和最小状态；不再调用 TUN、反复关闭/重开接口或尝试卸载受损驱动。不以 shell 仍能响应当作内核健康，按预定恢复权限重启 |
| USB 掉线或 ADB 命令超时 | 先保存主机最后时间、USB 变化和部分日志；停止所有自动重连后重放。有限观察是否自行恢复，只做一个有界、不会触发自动恢复的探活；不能据此把再次加载当作恢复 |
| 内核未坏，但 adbd 无法创建 shell | 若恢复范围已明确允许模块重启，可由专用无自动后续操作的通道单独请求 `reboot:`。现有 CLI 的 `recover` 带 USB/AT 后续动作，不能直接替代此步骤 |
| ADB 也不能响应或整机硬锁 | 不假设 USB reset 能重启 SoC；由现场人员按事先确认的供电方式完成一次受控断电重启。未具备这项条件时，测试应在 S0 停止 |
| 重启后仍不枚举或不能正常启动 | 保留主机证据，停止反复上电、切换模式和试刷。现有 boot 分区读回不等于完整救砖固件；本方案不包含刷机、分区写入或恢复模式操作 |

采集配置没有硬件 watchdog 和 Magic SysRq，不能承诺卡死会自动恢复；`PANIC_TIMEOUT=5` 也不保证 Oops 会触发重启，且运行时值仍需只读核对。

### 重启/断电后的验收

重新核对目标身份、新 boot_id/uptime、内核版本/配置、USB/ADB 可用性、模块列表、misc/接口、挂载和暂存路径。确认 tun 未被重新自动加载，主网络及原业务恢复，再恢复先前主机服务。RAM 文件应在真正的完整重启后消失，但必须回读，不以 USB 重新枚举代替这个证据。

重启会中断业务，且故障内核未传出的日志可能永久丢失。重启后“设备恢复”与“测试通过”分开记录：发生 Oops、失联或必要恢复时，本轮运行测试应标为失败/中断，即使随后设备工作正常。

## 七、分项记录和本轮准备状态

使用 [运行记录模板](TEMP_LOAD_RUN_RECORD.template.md)，每项只能填“通过、失败、未执行、证据不足”，附原始日志路径。最终成功必须包含正常卸载和清理验收；若仅加载成功，则仅报告加载成功。

当前准备结果：驱动、配置和既有启动分区读回文件的本地摘要已重新核对；本方案及记录模板已准备。实时执行通道、日志读取器、TUN 测试器尚未实现/验收；设备当前连接、内存、RAM 挂载、业务和现场断电条件本轮未探测。因此**方案已形成，尚未满足实际加载前的全部条件**。
