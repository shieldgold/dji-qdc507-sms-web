# 短信与 VPN 共存内存优化及 E01 实测

本轮完成了测试工具的内存优化和验证，并执行一次实机临时测试。**完整 30 秒共存仍未通过**：6 组加密 ICMP + 短信网页检查成功，第 7 组 ICMP 成功后，HTTP 开始时触发原有内存下降停止线。客户端退出，原短信服务恢复并完成清理；未刷机、未设置自启、未替换模块短信程序。

结构化证据见 [E01 结果](runtime/coexist-memory-result-2026-11-14-E01.json)，上轮对照见 [D03B](COEXIST_TEST_2026-11-14_D03.zh-CN.md)。原始日志、凭据和可执行文件只保留在电脑私有目录，未纳入 Git。

## 优化范围及影响

上轮短信匿名内存在共存窗口内从 2428 增至 3100 KiB，charon 匿名内存约 344 KiB；第 10 次 ping 子进程启动后触发停止。因而本轮先减少工具开销，同时保留短信生产程序、监管循环、16 个 charon 工作线程、连接配置和采样基线位置。

1. 共存窗口的单次 ICMP、HTTP 改在 guard 内执行，消除每轮 20 次 fork/exec。ICMP 仍绑定预期 VIP、128 字节 payload、1 秒绝对期限，校验完整 IPv4/ICMP 回包；HTTP 仍仅访问本机 8787 的 `GET /`，2 秒绝对期限，限定头部/正文大小，仅记录状态、字节数和耗时。
2. 两种探测均使用非阻塞 socket，poll 最多 100 ms；等待前后继续检查内核日志、内存、短信/监管身份及 charon 存活。普通等待仍为原来的 250 ms。回调取消与普通端口未就绪分开，启动时遇告警或瞬时越线不能重试抹掉失败。
3. smaps 改用 512 字节缓冲逐步累计，正常输入仍读到 EOF，保留原有 131071 字节起拒绝的边界，并检查数值及累计溢出。移除 131072 字节静态预留；它此前仅部分触页，不能把该预留直接当作实测 RSS 节省量。

核心运行限制均未改变：暂存后启动至少 8192 KiB，可用内存不低于 6144 KiB，较原始基线下降不超过 3072 KiB，30 秒/10 组，80+3 秒期限、300 秒独立恢复、180 秒守护启动年龄、日志异常即停和精确进程归属检查。本轮按继续验证的授权，将既有 11776 KiB 准入仅绑定到 E01；工具全局默认仍为 12288 KiB。

## E01 实机结果

重新核验 USB、SIM READY、蜂窝默认路由、证书有效期、原监管及短信程序摘要后，三轮各 30 秒 USB 日志采集通过。独立恢复守护就绪后暂停原监管及短信子进程，准入读数为 **12052 / 12040 / 12040 KiB**。低复制暂存及所有摘要核验通过；53.364 秒后提交共存入口，符合原 180 秒限制。

证书 IKEv2/IPsec 建立成功，5 个预检加密 ICMP 通过。swanctl 退出后释放其 RAM 文件，守护先恢复时钟，再 CONT 原监管。新短信进程由原 PID 428/starttime 826 的监管循环启动，整个窗口及清理后身份保持一致。

| 实机指标 | 结果 |
| --- | ---: |
| 原始运行基线 | 9760 KiB |
| 停止时可用内存 | 6672 KiB |
| 下降量 / 允许值 | **3088 / 3072 KiB** |
| 超出下降线 | **16 KiB** |
| 距绝对 6144 KiB 下限 | 528 KiB，未触及 |
| 完成的 ICMP + HTTP 组合 | **6 / 10** |
| 窗口内成功的加密 ICMP | 7 |
| 第 6 组完成时刻 | 窗口开始后 15.446 秒 |

| charon 峰值，含 rusage | 1464 KiB |
| guard 实机采样 RSS 峰值 / 匿名峰值 | 152 / 56 KiB |

短信窗口采样 RSS 从 5796 增至 7328 KiB，匿名内存从 2536 增至 3060 KiB；停止后的原生采样达到 7480 / 3260 KiB。进一步清理阶段使用系统 awk 独立汇总 smaps，观察到 **7992 KiB RSS、3660 KiB 匿名内存**。charon 的窗口匿名内存为 336–340 KiB。

因此，工具节省量已得到验证，但短信进程的启动/后台运行增长及系统内存波动仍足以跨线。本轮短信增长节奏与 D03B 不同，不能用两个停止瞬间的可用内存差，推断整体稳定性改善；也不能把 RSS 与 tmpfs 文件大小简单相加。

服务端正式采样 80 次、0 错误，观察到本测试身份及 CHILD；专用 `in,ipsec` ICMP 计数 **15 → 27**，对应 5 个预检包和 7 个窗口包。最终测试 peer 已消失，其他会话未操作。采集按 `:put [...]` 明确输出，并在电脑以 active-peers 的 **`id`** 字段精确过滤；早期误用 `remote-id` 的一次查询已单独标为无效，不作为证据。

## 恢复与清理

停止后 charon 发送 DELETE，子进程回收，VIP、目标 /32、ipsec0 及运行目录移除。确认 TUN 引用为零且没有客户端进程后释放自有 RAM 文件，带日志普通卸载 TUN，并清理本轮字符节点和空目录。随后 30 秒日志检查通过，按白名单清理工具目录。

- 原监管身份、短信程序与启动脚本摘要保持一致，短信网页 200，SIM READY；清理后仍为同一新短信进程。
- boot ID、taint、内核配置、接口、地址、当前路由、DNS、规则及原内核模块最终对照通过。
- 首次路由对照出现一条 IPv6 目标项，随后在没有写路由的情况下自行消失；另建只读连接复核当前完整路由，与初始一致。该暂态差异保留在日志中。
- 主测试及只读复核分别为 4265 / 89 次 USB 传输，均 0 错误、0 短写；两个控制器和服务端采样进程均已退出。
- 未重启、强卸载、刷机、设置自启或持久安装客户端；没有发送短信或拨号。

## 短信分配路径的进一步证据

当前源码已设置 GOMAXPROCS=1、GC 百分比 20 和 12 MiB 软目标。`at.go` 的读取器对每个输入字节执行 `string(pending)` 及 `TrimLeft`，仅为识别 `>` 提示符。对当前源码使用电脑管道输入合成行：258 字节/行、1000 行，在 Go 1.25.6 darwin/arm64 下测得 **34625 B/op、226 allocs/op**。没有连接 AT 设备或使用真实短信。

这是可重复关注的分配热点；它衡量分配流量，不是驻留内存，且未证明当前源码与模块二进制逐字对应，也未通过实机堆剖析证明它是本轮增长的全部原因。本轮没有修改或替换短信程序。

下一阶段应先验证 AT 提示符识别的无分配实现，覆盖 CR/LF、无换行提示符及完整 PDU 行语义，并采集短信堆、栈和回收指标；再为短信程序本身准备受控临时替换与恢复验证。现有停止线继续保留，当前结果不构成长时间共存或短信实际收发验收。
