# 11.5 MiB 单轮准入共存实测：D03 / D03B

用户明确允许本轮把上传准入降至 **11776 KiB（11.5 MiB）**，其他停止条件不变。本轮确实建立了蜂窝直连证书 IKEv2/IPsec，并恢复原短信服务共同运行；完成 **9 组加密 ping + HTTP 200** 后，在第 10 组触发原内存下降停止线，**未通过完整 30 秒验收**。

结构化证据见 [coexist-runtime-result-2026-11-14-D03.json](runtime/coexist-runtime-result-2026-11-14-D03.json)。原始日志在电脑受保护的 `ike-validation-local/runtime-logs/`，未将凭据、其他用户的会话或短信正文提交 Git。

## 本轮例外及验证

- 默认准入仍为 12288 KiB。本轮例外由 `--client-admission-kib 11776 --approve-lower-admission-for RUN_ID` 显式选择；批准字段必须与包的 run ID 相同，绑定器拒绝跨轮沿用或篡改停止条件。
- 启动门槛仍为 8192 KiB，运行可用内存下限仍为 6144 KiB，较启动基线下降上限仍为 3072 KiB；日志异常即停、80+3 秒截止、300 秒独立恢复及精确进程身份检查均保留。
- 仅修改电脑 Python 打包、绑定校验及对应测试。47 项 CPU 测试中 46 项通过、1 项原有 binfmt 环境检查跳过；静态 ARM 守护、客户端、日志探针和 tun.ko 均沿用已验证二进制。守护 SHA-256 为 `be9e3c4f79042e42bd6a85696f38fc82cae936176d83ad65dae78aca253c0844`。

## D03：启动年龄保护及恢复

D03 的暂停后采样为 12116 / 12156 / 12156 KiB，满足本轮 11776 KiB 门槛。文件校验和临时 TUN 加载成功，但阶段调度过慢，恢复守护年龄超过原有 180 秒启动限制，原生入口返回 65，未创建 VPN 运行目录或发起 IKE。

因入口在 LOGGER_READY 前结束，电脑控制器依约将通道标为不可重试，原通道的卸载请求没有发送到模块。关闭原控制器后，新建恢复连接并先读回现场。独立守护已在 300 秒到期时自动恢复原时钟并 CONT 原短信监管；原监管保持 PID 428/starttime 826，短信重新启动并恢复 HTTP 200。

确认没有客户端进程、VPN 运行目录和 TUN 引用后，先释放已不用的客户端 RAM 文件，把可用内存由 6624 KiB 恢复至 8976 KiB，再带日志普通卸载 TUN、清理本轮节点和目录。恢复后 30 秒日志及地址、路由、DNS、规则、boot ID、taint、原内核模块对照通过。没有强卸载或重启。

本次延迟没有作为放宽时间条件的理由。清理后，在同一已授权临时测试中使用新 run D03B 重试，将关键阶段改为逐卡等待、检查结果后立即推进，任一失败仍停止，避免调度空档。

## D03B：实际共存窗口

三轮各 30 秒日志检查通过后，重新验证原监管和新短信进程身份。独立恢复守护 READY 后暂停短信，采样 **12116 / 12104 / 12104 KiB**，均满足本轮准入。低复制暂存模型峰值额外 2393142 字节，11776 KiB 入场时预留 256 KiB 辅助余量后，模型剩余 9182 KiB；实际启动前读数约 9792 KiB。

全部文件校验后，以 60 秒内的新鲜启动 ID/进程身份绑定控制文件。普通 insmod、日志交握和设备号 `10:200` 检查通过。在恢复守护 READY 后 **72.429 秒** 提交原生共存入口，符合 180 秒限制。

客户端直接经 `rmnet_data0` 使用 UDP 500，NAT-T 转 UDP 4500；预期 VIP 为 `10.77.77.39`，唯一受保护目标为 `10.10.40.1/32`。证书认证、IKE/CHILD 和 5 个预检加密 ping 通过。退出管理程序后释放 swanctl RAM 文件，再精确通知恢复守护；日志证明先恢复时钟、再 CONT 原监管。新短信 PID 1986/starttime 1001659、PPid 428。

随后短信与 VPN 同时运行，9 组加密 ping 与网页检查均成功，最后一组完成于窗口开始后 24.749 秒。第 10 个 ping 子进程在窗口开始后 27.154 秒创建，紧接着出现内存停止记录；STOP 行没有独立时间戳，因此只能说在约 27 秒时停止，不能写成完整 30 秒通过。

## 恢复、采集边界和清理

在确认客户端已退出、TUN 引用为零后，先释放已不用的客户端文件以回收 RAM，再带日志普通卸载 TUN、清理本轮字符节点及空目录。随后采集 30 秒日志，按白名单清理全部临时工具并核对：

- 原监管身份不变，新短信进程在 VPN 结束及最终清理后保持同一身份，网页 HTTP 200，SIM READY。
- 本轮目录、运行目录、TUN 模块/节点、ipsec0/VIP/目标路由和本轮进程无残留。
- 接口、地址、IPv4/IPv6 路由、DNS、防火墙规则、boot ID、taint 和原内核模块与各自基线一致；短信启动脚本及二进制哈希不变。网络计数自然增加，不作为规则变化。
- D03、恢复连接、D03B 分别记录 3452、343、4351 次 USB 传输，均为 0 错误、0 短写；控制器和服务端只读采样进程均已退出。

服务端监听留下了专用规则的有效计数；但当时 `active-peers print as-value` 没有经 `:put` 输出，54 次空身份输出不能作为活动身份快照或空闲证明。最终改用显式输出全部 peer 值、在电脑内过滤目标身份，确认没有测试 peer；未保存或披露其他会话。后续采集应使用 `:put [/ip ipsec active-peers print as-value]`，参见 [MikroTik 官方脚本说明](https://help.mikrotik.com/docs/spaces/ROS/pages/47579229/Scripting)。本轮加密流量证据来自客户端认证/SA/收发日志及服务端专用 `ipsec-policy=in,ipsec` 规则计数，不能用空身份输出替代。

本轮没有刷机、常驻安装或设置自启，也没有调整其他服务或降低运行停止线。结论是协议与进程可以短时间共存，**当前临时 RAM 部署没有通过要求的资源余量验收**；未做真实短信发送、登录后的业务验收、长期稳定性或断网重连测试。
