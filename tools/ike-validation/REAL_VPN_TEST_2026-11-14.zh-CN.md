# QDC507 IKEv2/IPsec 专用证书实机验收

2026-11-14，原生 strongSwan 6.1.0 已在 QDC507 上使用专用 RSA 证书，完成 IKEv2 认证、IPsec CHILD_SA 建立、地址分配、双向加密 ICMP 和 CHILD_SA 重协商。模块使用既有 GCC 4.9.3 构建的 `tun.ko`，数据面为 `kernel-libipsec`，不依赖模块缺失的内核 XFRM/ESP。

本次外层 UDP 经过 Mac 的受限中继。模块没有蜂窝默认路由，因此本结果证明客户端及 TUN 数据面可工作，尚未证明 4G 直连、短信服务与 VPN 同时运行、长期负载或公网出口。测试期间按授权暂停短信服务；测试结束后恢复。

## 实际收发证据

- IKE：AES-256-CBC / HMAC-SHA-256 / PRF-SHA-256 / MODP2048；证书认证 RSA。
- ESP：AES-256-CBC / HMAC-SHA-256，UDP 封装；与服务器现有策略一致，无 PFS。
- 选择器严格为 `10.77.77.39/32 === 10.10.40.1/32`；只创建一个临时 `ipsec0` 和目标 `/32` 路由。
- 第一组 5 次 ping：每次数据区 128 字节，收发 5/5，0 丢包；旧 CHILD 双向各 780 字节、5 包。
- CHILD 重协商确认：旧 SPI `8a070230_i / 272ba23d_o` 换为 `75865abe_i / f5545879_o`；日志明确记录 rekey，新旧 SA 的计数分别可见。
- 重协商后第二组 5 次 ping：收发 5/5，0 丢包；新 CHILD 双向各 780 字节、5 包。
- 正常 IKE DELETE 得到响应，客户端退出后 VIP、TUN 和目标路由消失。

`kernel-libipsec` 会自行创建选择器路由，独立于普通的 `install_routes=no` 开关。监督器因此检查新接口仅有精确目标 `/32`，拒绝宽路由，并在结束后验证无残留。没有添加主默认路由或修改 DNS。

每轮实测前均通过三次 30 秒连续日志采集，载入、运行、卸载及恢复后继续采集。两轮共 7703 次 USB 传输，均未记录传输错误；日志中未捕获新增 Oops、WARN、BUG、OOM 或序列缺口。每次销毁 `ipsec0` 的两条 RMNET unregister 信息与此前已核实的通知路径一致。

## 时间、恢复与清理

模块原始系统时间为 1980 年，证书验证需要当前时间。短信应用的登录有效期依赖该原始时钟，所以没有永久校时：先用独立 `resume-clock` 守护保存实时时钟与单调时钟，再暂停原监管进程及短信子进程；仅在证书测试窗口临时使用正确时间。

正常结束或守护超时，均先把时钟恢复为“原实时时间 + 单调经过时间”，再在 PID、启动 tick、可执行文件和参数核对后 CONT 原监管进程。此顺序已在独立 ARM VM 中验证自动超时及手动结束两条路径，实机日志也记录了先 `CLOCK_RESTORED`、后 `RESUME_SENT`。未写 RTC、校时服务或启动配置。

两次短信暂停窗口均在 240 秒限制内，独立恢复守护上限为 300 秒。实机完成以下回读：

1. charon、swanctl、测试 ping 和恢复守护退出；`tun.ko` 经普通 `rmmod` 卸载，没有强制卸载。
2. 临时 `/run/qdc-ike`、本轮 `/run/qdc-tun-*`、私钥、证书、客户端文件、`/dev/net/tun` 及测试创建的空 `/dev/net` 均清除。
3. VIP、`ipsec0`、目标 `/32` 路由及 UDP 500/4500 监听无残留；Mac 的中继和 USB 控制器已关闭。
4. 原短信监管 PID 431 保持原启动身份并恢复运行，新短信子进程启动；网页实测 HTTP 200。
5. boot ID 仍为 `0d8f027b-94e0-4bb5-bd2f-df52ac937d78`，taint 保持原值 4608；未重启。
6. 原接口地址、配置路由、DNS 文件哈希和防火墙规则不变。第一轮仅有 IPv6 mDNS `ff02::fb` 动态缓存项自然过期；比较时单独排除此缓存及防火墙计数。

本次没有刷机、持久安装客户端或驱动、设置开机加载、修改模块默认路由或 DNS。短信正常运行期间还可能有模块原服务自身的持久写入；本记录只说明本测试没有执行刷机或持久配置操作。
